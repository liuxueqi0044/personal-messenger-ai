## 0. 请先区分三个事实

1. 控制平面已有较完整的代码和离线测试，不等于 QQ/微信自动聊天已经可用。
2. QQ 当前只完成有限的后台只读能力和“当前可见聊天”的人工短期租约；一次只限定一个当前会话。
3. 当前真实发送次数为 0，`automatic_eligible=false`。Q4 草稿写入、Q5 发送及发送后验证尚未实机完成。

## 1. 项目最初目的

目标是在一台用户自己的 Windows 电脑上，为已经登录的个人 QQ 和微信客户端建立多联系人个人聊天助理：

- 后台观察新消息，为不同联系人维护隔离的上下文、记忆、人设和行为规则；
- 根据语境决定不回复或生成 1～3 条自然消息，而不是每条入站都强制回答；
- 短消息可短回，长回复首发至少等待 30 秒，并允许在等待期间因新消息、人工回复或切换会话而取消；
- 最终按队列串行处理多个联系人，而不是只服务一个人；每次执行必须重新锁定和验证目标，禁止串聊和重复发送；
- 面向用户本人可见、可暂停、可审计的沟通辅助。人格规则主要用于日常及潜在恋爱关系沟通，但关系确认、金钱、隐私、未成年人、医疗法律、自伤威胁等高风险内容必须转人工；
- 不争夺桌面：不抢前台，不用全局鼠标键盘，不占剪贴板，不要求第二台电脑或虚拟机；QQ/微信可以由用户正常使用；
- 尽量采用官方客户端公开可访问的窗口/无障碍能力，不使用私有协议、Hook、注入、进程内存读取、验证码绕过或针对风控的对抗逻辑；
- 无法承诺零封号，只能通过低频、明确权限、专用账号验收和失败关闭降低误发、打扰及账号风险；
- 优先复用成熟开源组件，但安全边界、维护成本和版本适配优先于“为了复用而复用”。

期望的最终处理链：

```text
多会话观察 → 稳定联系人绑定 → 每联系人上下文/记忆/规则
→ ReplyPlan（0～3 条）→ 节奏等待 → 到期重新验证
→ 单联系人执行锁 → 草稿写入和读回 → 一次性提交
→ 发送后验证 → 审计/失败关闭 → 处理队列中的下一个联系人
```

模型、Codex、WebUI 和 MCP 均不应直接拥有无约束的 `send(text, target)`。

### 2.2 QQ Q0/Q1/Q2 只读前半段

- 已认证本机 QQ 版本：`9.9.26.44343`；
- Q0 能校验 QQ 进程、PID/启动时间、exact HWND、登录/窗口/模态状态和环境指纹；
- Q1 能在当前最大化布局下建立脱敏 UIA 结构和 selector 摘要；
- Q2 的消息观察、方向/去重契约已有代码和离线测试；实机只证明有限的当前会话只读可行，尚未完成 500 条多场景夹具验收；
- metadata helper 只输出 PID、进程启动时间、HWND、窗口状态、当前会话头摘要和稳定结构摘要，不输出昵称、聊天正文、坐标或像素。

### 2.3 QQ 人工短期会话租约

因为尚无可靠的永久联系人 ID，当前提供一个严格降级方案：

- 用户手动打开并最大化 QQ、选择目标聊天；
- 打开 `http://127.0.0.1:8765/qq/session-lease`；
- 首屏立即显示，点击“检测当前 QQ 会话”后做约 30～35 秒只读校验；
- 不要求、也拒绝接收对方 QQ 号；系统按当前 scope 和随机 nonce 生成匿名短期 HMAC；
- 用户必须再次勾选确认当前可见聊天；prepare、confirm、status 都重新验证 scope；
- QQ 重启、切换聊天、窗口/header/selector/环境漂移、读取错误、到期或撤销都会使租约失效；
- 当前实现最多允许一个 active lease；它不是永久联系人绑定，不能支持多人自动切换；
- 租约不提供写入或发送能力，`automatic_eligible=false`。

本地 WebUI 已修复“首次打开像卡死”的问题：耗时检查由首屏 GET 移到按钮触发的 POST，并在线程池执行。首屏浏览器实测可正常显示，直接 prepare 实测返回 200，约 33.2 秒。

## 3. 已尝试但判定 NO-GO 的路线

### 3.1 资料窗读取稳定 QQ 号

曾尝试通过当前会话标题的 UIA `InvokePattern` 打开联系人资料窗，读取明确标注的 QQ 号并立即关闭。实机结果：

- QQ 被带到前台，违反“不争夺桌面”；
- `WindowPattern.Close` 不能可靠证明资料窗已恢复关闭；
- 因而返回 `RESTORATION_FAILED`，未创建绑定、未发送。

这条路线在当前 QQ 版本上停止，不应未经新证据直接重试。

### 3.2 PrintWindow / exact-HWND BitBlt

为了在不导航的情况下用头像作为第二身份信号，尝试对 exact QQ HWND 采集头像 ROI：

- `PrintWindow` 得到黑/纯色帧；
- `GetWindowDC(targetHwnd) + BitBlt` 也不能取得可用帧；
- 未使用桌面 DC、整屏截图或全局输入。

### 3.3 Windows Graphics Capture

已经实现并构建 managed .NET 10 exact-HWND WGC sidecar：

- 使用 Vortice.Direct3D11 `3.8.3`；
- 帧池/会话能够创建，CaptureService 可启动；
- `Programmatic` 和 `WithoutBorder` 权限均为 Allow；
- 但 QQ、Chrome、ChatGPT 三类窗口均没有帧交付；
- 外部 WgcSharp `1.1.1`、`WgcOnly` 原始 COM 探针独立复现 `NO_FRAME`；
- 完整 Windows 重启后结果不变。

因此目前证据不支持“只差一个权限开关”。更像是当前主机/OS/驱动/捕获链的帧交付问题。WGC 代码应作为诊断资产保留，但已从生产依赖中移除。

另有一个独立问题：Visual Studio Build Tools 2022 安装时被 Smart App Control/Config CI 阻止 UCRT x86 MSI，外层 `1603`、内部 `1625`，导致 v143/MSVC/Windows SDK 未安装。这个 C++ 工具链问题不等于 managed WGC 无帧的根因，不能混为一谈。未关闭系统安全控制。

## 4. 当前真正缺少的“眼睛”和“手脚”

### 4.1 眼睛/采集层缺口

- 无法可靠、持续地发现所有有新消息的 QQ 会话；
- 只能读取当前可见聊天，不能安全遍历多人会话；
- 没有不抢前台、可跨切换/重启验证的稳定联系人第二信号；
- 没有完成 500 条真实只读夹具的方向、时间、水位、去重和错会话归属验收；
- 微信尚无新的实机证据，应独立验证，不能继承 QQ 结论。

### 4.2 手脚/执行层缺口

- 没有认证唯一聊天 composer；
- 尚未验证后台语义写入（UIA Value/Text/LegacyIAccessible 等）是否可行；
- 没有“写入草稿 → 从同一 composer 读回 → 哈希一致 → 安全清空”的 Q4；
- 没有唯一提交动作、一次性令牌和发送后本方消息证据的 Q5；
- 没有经过专用测试账号的 200 次草稿及 100 次发送零错人/零重复验收；
- 因此多人自动回复、单人自动回复目前都没有解锁。

## 5. 什么可以推翻，什么不建议推翻

### 建议保留

- M0～M13 控制平面的领域边界；
- 每联系人隔离、0～3 条回复、节奏等待和取消机制；
- 到期重新验证、一次性授权、单提交锁、发送后验证；
- loopback WebUI、DPAPI、审计、暂停、版本隔离和失败关闭；
- WGC/GDI/profile 探针代码作为负面证据和回归诊断资产。

### 可以重新设计或替换

- QQ/微信平台 bridge；
- 多会话发现和稳定联系人绑定策略；
- 当前单会话 lease 的产品形态；
- Q4/Q5 执行 sidecar；
- 官方 API、本机语义无障碍、独立 Windows 会话或其他不抢桌面的承载方式。

### 不应无证据降级采用

- 根据昵称、列表位置、树序号或固定坐标猜目标；
- `SendInput`、全局键鼠、占用剪贴板和强制置前；
- Desktop Duplication/整屏截图后坐标点击；
- 私有协议、Hook、注入、进程内存读取或验证码绕过；
- 在主账号上直接做自动发送 POC。

如果独立评估证明在当前个人 QQ 客户端上无法同时满足“多人、后台、不抢桌面、稳定身份和低误发”，应明确把产品停在 L1（真实观察/候选草稿/人工发送），而不是偷偷降低身份和发送门槛。

## 6. 请接手模型重点回答的问题

请不要直接开始重写代码。先基于现有实现和实机证据，输出一份独立架构复审：

1. WGC 的跨应用 `NO_FRAME` 最可能属于权限、Windows 版本/驱动、实现错误还是平台限制？请为每个判断给出可证伪的最小实验。
2. 是否应该彻底放弃 WGC 生产路线，还是只需修复/替换 sidecar？现有负面证据中哪些充分，哪些仍有缺口？
3. 在不抢前台、不用全局输入、不使用私有协议的约束下，个人 QQ `9.9.26.44343` 是否存在可靠的多人会话发现、稳定身份和后台 composer 写入路径？
4. 请比较至少以下路线：
   - 纯 UIA/IAccessible 语义适配；
   - 其他 exact-window、不会捕获桌面的 Windows API；
   - QQ/微信官方机器人、开放平台、客服或企业接口（明确说明是否适用于个人聊天）；
   - 本机独立 Windows 会话、沙箱或 VM（说明是否真的必要以及对用户体验的代价）；
   - 只做 L1 草稿助手、发送永久人工确认。
5. “手脚”应该做成什么隔离进程和最小接口？至少给出 composer 定位、草稿写入、读回、清空、提交、发送后验证和不确定状态的协议。
6. 怎样从单 active lease 演进到多人队列，同时保证同名、改名、列表重排、新消息插队、QQ 重启和版本升级都不会串聊？
7. ChatGPT Work/云端模型只能作为规划与模型层，还是能替代本机数据面？请明确它如何安全访问本地 QQ，以及断网、延迟和权限边界。
8. 给出明确结论：
   - 保留现有架构、只替换平台 bridge；
   - 局部重构；
   - 或推翻重做。

结论必须包含：方案对比表、推荐路线、拒绝路线、最小 POC、每模块输入输出、独立验收标准、账号风险、预计工程量和停止条件。不要把“能枚举控件”“能创建捕获会话”或“能输入一次文字”误当成可上线能力。

## 7. 建议的最小下一步

在得到新的可靠平台信号之前，不建议继续堆 WGC 变体。更有价值的下一步是用专用测试 QQ 做两个互不依赖的短 POC：

1. **Q2 多会话发现 POC**：只读、零切换、零输入，证明能稳定识别会话、新消息和唯一联系人；否则多人后台自动化直接停止。
2. **Q4 composer POC**：只针对用户手动选中的专用测试聊天，尝试后台语义写入、读回和清空，绝不提交发送；若会抢前台、无法唯一定位或不能读回，执行层判定 `UNSUPPORTED`。

只有两者分别通过，才值得进入 Q5 专用账号发送验证。两个 POC 都不应依赖主账号，也不应改变现有控制平面。
