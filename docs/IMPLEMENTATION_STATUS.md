# Implementation status

This document separates implementation, offline verification, controlled-environment evidence and production readiness. A passing test does not silently promote a capability to a higher assurance level.

The current refactoring baseline is [ARCHITECTURE-V2.md](ARCHITECTURE-V2.md), dated 2026-10-01. V2 assigns fragile contact navigation to a bounded vision loop and retains deterministic observation, scheduling and delivery. The independent V2 runner, production assembly and supervisor opt-in are implemented. Controlled production-assembly observation has passed; actual V2 delivery remains unverified. The failed cold-prepare/abort test draft has been manually cleared and its exact ownership record settled after fresh empty-composer verification. Automated draft recovery remains unverified. Runtime remains stopped and paused.

[ARCHITECTURE-V1.md](ARCHITECTURE-V1.md) remains the earlier product and persistence baseline. Neither design document upgrades any implementation or live-verification status below.

## V2 implementation checkpoint, 2026-10-02

- Strict navigation targets, masked screenshot metadata and a closed one-action model schema are implemented. The Responses provider bounds network calls and rejects unrelated fields, tool calls and stale results. A single synthetic live `deepseek-flash` request selected the expected row in 1.626 s. This provider required a flat primitive JSON schema; the public internal action contract remains unchanged. No QQ data or UI action participated in that test.
- The guest backend captures only the exact QQ HWND using `PrintWindow`. Contact name fragments and the search edit are the only allowed visible regions; preview, body and composer pixels are masked. One actual full-window capture returned a nonblank image in 2.518 s. This component evidence does not establish navigation after a list reorder.
- The native foreground check now follows `GA_ROOT` and requires the exact main HWND and QQ process. An actual Chromium renderer child was verified as belonging to that root. A different hidden QQ root is still rejected. `ROOTOWNER` and process identity alone do not authorize the main window.
- Profile capture reads the labeled ID in the normal QQ profile UI, hashes it locally, closes the unique new profile window and requires unchanged original header and chat structure. Repeated actual captures matched the same opaque identity; one optimized successful sample took 8.979 s. A full V2 lease requires independent fresh Python witnesses before and after the capture. Deployment uses externally supplied HMAC identity anchors; no production binding is automatically enrolled.
- Actual local current-chat inspection returned one selected row, a direct conversation, complete zero group markers, a proven latest message tail and an empty composer in 2.94 s. This is a read-only component result, not an authorization to send.
- Navigation task and episode persistence preserves the original pending input across bounded retries and restart. The optional due preflight precedes M9/Hub authorization. Temporary navigation failure defers the original segment; attention and existing-operation recovery are held separately. Claim nonce checks fence both late READY/recovery results and transactional settlement. Runtime and pacing tests passed together (368 tests); an independent review and 31 focused cases confirmed the stale-claim settlement defect is closed.
- A real subtree inspection exposed an existing UIA cache defect: temporary COM wrappers were cached by Python object ID without being retained. Object ID reuse could transfer another element's type/class/pattern to a new wrapper. The cache now retains all cached controls for the read phase and releases them at close. Subsequent subtree indexing preserves relative ancestor matching and avoids repeated scans within that phase. Controls are not retained across a model wait or UI action.
- `scripts/run_vm_runtime_v2.py` assembles the navigation service, current-chat hybrid worker, staged preparation bridge and deterministic runtime. The existing guest supervisor selects it only with explicit `--hybrid-settings` and repeatable `--active-binding` arguments. The settings are an absolute immutable JSON snapshot, fenced by a fixed `--expected-hybrid-settings-sha256`; frozen business configuration, canonical publication and session-revision checks remain separate. The Start wrapper's build/start phases still select V1.
- A V2 desktop round has one original 45 s UTC/monotonic budget, including cleanup; preparation retains a 20 s write reserve. Cold preparation precedes authorization and keeps exact draft ownership in the same worker. Adoption follows the unchanged 10 s authorization boundary. Before COMMIT IPC, durable commit intent is persisted and the current runtime guard is explicitly refreshed. VERIFY retires and reaps the prior worker before starting a fresh process with a new epoch. An ambiguous send remains held; no automatic send retry is introduced.

Navigation now runs full independent N2 verification immediately after a candidate click. Scope reads no longer perform an unused full UIA tree scan. Capture may discard a failed read and rebuild one complete fresh read only for the exact `UIA_E_ELEMENTNOTAVAILABLE` HRESULT `-2147220991`; other errors and a second invalidation still reject. This read recovery cannot retry input or renew scope, proof lifetime or the original deadline.

The shared `current_chat_structure` projection now removes only the composer's exact `ProseMirror-focused` and `is-empty` class tokens from structural identity. It retains role order, all three RuntimeIds, header/message classes and every other composer token. Focus and empty/owned contents remain independent input-boundary checks; full N2 correlation, profile HMAC and ambiguity/group rejection remain required.

Windows candidate clicks and search opening now use an explicit `verified_click(frame, region, x, y, deadline_at, cancel_event)` producer capability. One child command independently checks the exact owned frame/region and point, obtains a complete fresh UIA/PrintWindow ROI proof, compares frozen/current pixels and performs the final guard/native checks before one click. Scope checks and postcapture remain. The actual-module offline chain uses two PrintWindow captures and four UIA phases per execute, compared with three captures and six phases on the preserved generic path. ## Architecture implementation, 2026-10-01

The first W0 changes are implemented and offline-tested:

- Runtime configuration builds now hold the same ownership mutex as the runner. Frozen manifest/config rejection happens before registration changes. Publication uses a write-ahead rollback record, startup fences, atomic file replacement, and interrupted-build recovery; existing business databases are not rolled back or reset.
- Parent request events and child UI stages persist to bounded, content-free diagnostic files even without stdout. First/last failure and last successful request remain available across subsequent requests and worker replacement. These diagnostics do not replace the execution journal.
- Windows UI children spawn with the installed `pythonw.exe`; the multiprocessing executable setting is restored after the spawn. A bounded guest probe passed HEALTH with foreground unchanged. Its subsequent failed OBSERVE retained first/last failure and the source call chain with zero diagnostic-write errors.

The full suite passed after the startup-fence additions (1508 passed, 2 skipped). Live installation and new driver acceptance are tracked separately; no new real delivery is claimed by these results. W1–W5 and the remainder of operational-entry consolidation are not marked complete.

A subsequent live probe isolated the selection failure: the selected row's background and dominant ratio matched, but rounded-corner antialiasing changed its distinct-colour count from 12 to 14. The versioned `horizontal-strips-v2` profile samples two fixed background strips away from text and corners. It requires all 1744 pixels to agree and retains the exact runtime target, unique selected row, two control rows, repeated samples and independent header checks. Twenty visible rows in two guest samples and two unselected-row hover probes reproduced the three distinct uniform backgrounds. The QQ adapter tests passed (625 tests); end-to-end guest observation with this change is a separate gate.

The first W1 session-lifecycle step is implemented. An explicit `--refresh-current-session` operation can update QQ process/window/row locators in a stopped, paused generation after checking its expected ID and config digest. Every existing contact must have fresh evidence with unchanged stable identity. Immutable, hash-linked session snapshots preserve the original generation, adoption boundaries, persona, policies and business databases. Runner validation and supervisor startup select the current session snapshot; ordinary configuration builds cannot silently refresh it. The integration suite passed (1620 passed, 2 skipped) before the subsequent row-enumeration optimization. Guest publication and real delivery remain separate acceptance gates.

Read-only guest diagnostics then isolated repeated full-window UIA enumeration as the main observation cost. Each row enumeration now has an independent short-lived read phase, caching duplicate property reads only within that enumeration and returning only IDs and rectangles. Hover and pixel sampling retain no live controls, and each later stability sample obtains a fresh root. One complete enumeration may be rebuilt on `UIA_E_ELEMENTNOTAVAILABLE`; other failures, repeated invalidation, changed targets and expired deadlines remain failures. Stage logs distinguish selection before/after content reading. This optimization does not reduce identity checks or extend request deadlines; its live latency must be measured separately.

These limited samples establish a read-only baseline, not sustained reliability or delivery readiness. ## Implemented

| Area | Status | Evidence boundary |
|---|---|---|
| Domain kernel and durable Hub | Implemented | Commands, events, inbox/outbox behavior and replay invariants are covered by automated tests. |
| Conversation observation | Implemented | Read-only adapters, monotonic cursors and normalized conversation events are available. |
| Multi-contact isolation | Implemented | Memory, plans, pacing state, operation IDs and ledgers are scoped by conversation. |
| Structured reply planning | Implemented | Providers must return schema-valid `ReplyPlan` objects; free-form text cannot directly authorize delivery. |
| Deterministic policy | Implemented | Eligibility, consent, pause state, evidence freshness and one-time authorization are checked outside the model. |
| Durable pacing | Implemented | Delays, segmentation, recovery and fairness are persisted and revalidated at execution time. |
| Delivery state machine | Implemented | `PREPARE → COMMIT → VERIFY` includes idempotency and an explicit `UNCERTAIN` quarantine state. |
| Local Web UI and MCP gateway | Implemented | Both are loopback/least-privilege control surfaces and expose no unrestricted send primitive. |
| Security and privacy controls | Implemented | DPAPI-backed secrets, redaction, evidence TTL, incident handling and metrics allow-lists are included. |

## Controlled environment

- A supervised direct-message path has been exercised in an isolated Windows test environment.
- Visual selection is bounded to a certified contact-row crop and is followed by fresh-process identity verification.
- The public snapshot omits contact identities, message text, account identifiers, screenshots and runtime evidence paths.
- Desktop-client compatibility is profile-specific; a logged-in client alone is never considered sufficient proof.

## Deliberately not production-ready

- Persistent unattended sending remains disabled pending longer soak testing and version-specific compatibility evidence.
- Group conversations are outside the automatic-send scope and must fail closed.
- Any ambiguous commit, stale observation, identity mismatch or incomplete verification stops execution and requires review.
- Real credentials, private chat data and deployment state are not distributed with the repository.
